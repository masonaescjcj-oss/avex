# راه‌اندازی AVEX Pay — از صفر تا لایو

این فایل تنها چیزی است که برای بالا آوردن سیستم لازم داری. هر گام سه چیز دارد: **چه کاری**،
**دستور دقیقش**، و **اگر انجامش ندهی چه چیزی خراب می‌شود** — بخش سوم مهم‌تر از دو تای اول است،
چون تقریباً همهٔ چیزهایی که در این لیست غایب باشند به‌جای خطا دادن، **سکوت** می‌کنند: سیستم سالم
به‌نظر می‌رسد و کار نمی‌کند.

## کوتاه‌ترین راه: یک اسکریپت به‌جای گام ۰۲ تا ۰۶ و ۱۱ و ۱۲

اگر نمی‌خواهی سیزده گام را دستی جلو بروی — و دلیلی هم ندارد — روی سرور این را بزن:

```bash
git clone <repo> /opt/avex && cd /opt/avex

sudo bash deploy/install.sh --selftest   # فایل‌هایی که می‌سازد را در یک پوشهٔ موقت می‌سازد و چک می‌کند
sudo bash deploy/install.sh --check      # به سرور نگاه می‌کند و می‌گوید چه چیزی عوض می‌شود
sudo bash deploy/install.sh              # انجامش می‌دهد
```

چه کاری می‌کند: نود ۲۲ را نصب می‌کند، کاربر سرویس را می‌سازد، کد را می‌گیرد و بیلد می‌کند،
فایل تنظیمات را با جواب‌های تو می‌نویسد (و `MEMO_SECRET` را خودش می‌سازد)، کلید تسویه را
می‌سازد و با بهترین روشی که systemd آن سرور بلد است سر جایش می‌گذارد، هر دو یونیت را
می‌نویسد، Caddyfile را می‌نویسد، مایگریشن می‌زند، `preflight` را نشان می‌دهد، **API را اول و
واچر را بعد** بالا می‌آورد، و آخرش حساب ادمین را می‌سازد.

سه چیز از تو می‌خواهد: رشتهٔ اتصال دیتابیس، `SMTP_URL`، و یک ایمیل برای هشدارها. بقیه پیش‌فرض
دارد.

- **هیچ رازی را دوباره نمی‌نویسد.** فایل تنظیماتی که وجود دارد دست‌نخورده می‌ماند مگر با
  `--reconfigure` (و آن هم نسخهٔ قبلی را کنارش نگه می‌دارد). کلید تسویه‌ای که وجود دارد
  **هرگز** دوباره ساخته نمی‌شود — کلید جدید یعنی کیف پول جدید، و موجودی روی قدیمی است.
- **هیچ رازی را چاپ نمی‌کند.** ورودی‌ها با echo خاموش خوانده می‌شوند و با مود ۰۶۰۰ نوشته.
  تنها چیزی که چاپ می‌کند **آدرس** کیف پول گس است، چون باید شارژش کنی.
- **دوباره اجرا کردنش بی‌خطر است.** همان اسکریپت راه به‌روزرسانی به کامیت جدید هم هست.

گام‌های ۰۱ (دیتابیس)، ۰۷ (اولین فروشنده)، ۰۸ (تست با پول واقعی)، ۰۹ (وردپرس) و ۱۰ (دیپلوی
قرارداد) کارهایی‌اند که اسکریپت نمی‌تواند بکند — حساب Supabase، مرورگر، کیف پول واقعی.

بقیهٔ این فایل توضیح می‌دهد اسکریپت **چه می‌کند و چرا**، و اگر چیزی خراب شد جای نگاه کردن است.

---

گام‌ها به ترتیب اجرا نوشته شده‌اند. **بعد از گام ۸ می‌توانی روی TRON پول واقعی بگیری.**
گام‌های ۱۰ تا ۱۲ برای زنجیره‌های EVM (بایننس، اتریوم، پالیگان…) است و بعد از لایو شدن TRON
انجام می‌شود.

> فایل انگلیسی `docs/GO-LIVE.md` همین لیست کوتاه‌تر است و `docs/DEPLOY.md` توضیح می‌دهد چرا
> معماری این شکل است. اگر جایی بین این سه تناقض دیدی، **این فایل** تازه‌تر است.

## نقشهٔ کل سیستم، در ده خط

دو هاست، و این تقسیم اجباری است نه انتخابی.

**۱. صفحات ثابت — روی Vercel، همین حالا لایو است.** سایت معرفی، صفحهٔ پرداخت مشتری، پنل فروشنده
و پنل ادمین، چهار فایل HTML مستقل هستند. `deploy/build-static.mjs` می‌سازدشان و روی
**avexpay.net** سرو می‌شوند. کاری با این ندارید مگر تغییر متن.

**۲. گیت‌وی — یک سرور که همیشه روشن است (VPS).** دو پروسه، و هیچ‌کدام نمی‌تواند سرورلس باشد:

| پروسه | دستور | کارش |
|---|---|---|
| API | `npm run start --workspace @avex/api` | همهٔ روت‌ها + جاب‌های پس‌زمینه |
| واچر | `npm run watch --workspace @avex/api` | پایش زنجیره‌ها + تسویه |

**واچر** یک کرسر per-chain دارد که باید یکنواخت جلو برود و در reorg عقب برگردد. رانتایمی که
بین درخواست‌ها فریز می‌شود نمی‌تواند poll کند، و دو نسخهٔ همزمانش همان بازه را دو بار اسکن
می‌کنند و کرسر هم را خراب می‌کنند. (قفل می‌گیرد، پس نسخهٔ دوم خارج می‌شود نه اینکه دوبار
بخواند.) **تسویه** هم داخل همین پروسه است، چون nonce و صف را بین تلاش‌ها نگه می‌دارد.

**API** جاب‌های پس‌زمینه را روی تایمر خودش می‌چرخاند — درین وبهوک هر ده ثانیه، و هیچ
زمان‌بند میزبانی‌شده‌ای این‌قدر سریع شلیک نمی‌کند (کف Vercel Cron یک دقیقه است). خودِ روت‌ها
جای دیگری هم اجرا می‌شدند؛ اینجا هستند چون واچر همین‌جاست و هر دو همان کانکشن‌پول را
می‌خواهند.

**پایگاه داده:** Postgres. Supabase قبول است.

## قبل از شروع: چیزهایی که باید داشته باشی

- [ ] یک **Postgres** — Supabase (رایگان کافی است برای شروع) یا روی همان VPS
- [ ] یک **VPS** — کوچک کافی است؛ ۱ گیگ رم و ۱ هسته. جایی که به RPC زنجیره‌ها دسترسی دارد.
- [ ] یک **سرویس SMTP** یا سرور ایمیل خودت
- [ ] دامنه **avexpay.net** (داری) و دسترسی به DNS آن
- [ ] یک اپلیکیشن **Authenticator** روی گوشی (Google Authenticator، Aegis، ۱Password…)
- [ ] برای گام‌های EVM: یک کیف پول با موجودی توکن اصلی آن زنجیره

## گام ۱ — پایگاه داده

### روی Supabase

Project Settings → Database → Connection string → **URI**. دو رشته لازم داری:

- **`DATABASE_URL`** — رشتهٔ pooler روی پورت **6543** (برای درخواست‌های عادی، سریع‌تر)
- **`DIRECT_DATABASE_URL`** — رشتهٔ مستقیم روی پورت **5432**

**چرا دو تا:** pooler حالت transaction هر دستور را به هر کانکشنی که آزاد است می‌دهد. برای
درخواست‌های عادی درست است و برای مایگریشن غلط: این اسکیما `CREATE TYPE` دارد (enum)، و
`CREATE TYPE` از داخل pooler به شکلی شکست می‌خورد که **مثل خطای سینتکس در فایل مایگریشن**
به‌نظر می‌رسد — و ساعت‌ها دنبال باگی می‌گردی که وجود ندارد.

### مایگریشن

```bash
export DATABASE_URL='postgres://…:6543/postgres'
export DIRECT_DATABASE_URL='postgres://…:5432/postgres'
npm run db:migrate --workspace @avex/api
```

باید `migrations applied successfully` بدهد.

> **اگر انجام ندهی:** هیچ چیز دیگری در این لیست قابل تست نیست.

## گام ۲ — فایل تنظیمات

روی VPS، فایل `/etc/avex/api.env` را بساز. `/.env.example` در ریشهٔ ریپو **همهٔ** متغیرها را با
توضیح دارد؛ این حداقلِ لازم برای شروع با TRON است:

```ini
NODE_ENV=production
PORT=3000
HOST=127.0.0.1

DATABASE_URL=postgres://…:6543/postgres
DIRECT_DATABASE_URL=postgres://…:5432/postgres

# ⚠️ آدرس صفحات ثابت، نه آدرس API.
# لینک تأیید ایمیل می‌شود APP_URL/dashboard و لینک پرداخت مشتری APP_URL/pay/<id>.
# اگر این را روی api.avexpay.net بگذاری، هر ایمیلی که می‌فرستیم لینکِ 404 دارد.
APP_URL=https://avexpay.net

SMTP_URL=smtps://user:password@smtp.example.net:465
MAIL_FROM=no-reply@avexpay.net
MAIL_FROM_NAME=AVEX Pay
OPERATOR_EMAIL=ops@avexpay.net

# صفحات روی avexpay.net هستند و API روی api.avexpay.net — یعنی cross-origin.
CHECKOUT_ORIGINS=https://avexpay.net
DASHBOARD_ORIGINS=https://avexpay.net

# TRON یک JSON-RPC سازگار با اتریوم می‌دهد، پس در همین متغیر می‌آید نه جای دیگر.
EVM_RPC_URLS=tron=https://api.trongrid.io/jsonrpc

# راز پشت memo فاکتورها. حتماً عوضش کن: یک memo قابل حدس زدن یعنی یک غریبه
# می‌تواند پرداخت شخص دیگری را به نام خودش claim کند.
MEMO_SECRET=<۳۲ کاراکتر تصادفی>
```

برای `MEMO_SECRET`:

```bash
openssl rand -hex 24
```

> **اگر `MEMO_SECRET` را عوض نکنی:** مقدار پیش‌فرضش در ریپو نوشته شده و عمومی است.

## گام ۳ — ایمیل

`SMTP_URL` به شکل `smtps://user:password@host:465` (یا `smtp://…:587` برای STARTTLS).

دامنهٔ فرستنده **باید** رکورد **SPF** و **DKIM** داشته باشد. بدون این‌ها ایمیل به spam می‌رود، و
برای یک لینک تأیید، spam دقیقاً به‌معنای «نرسید» است.

> **اگر انجام ندهی:** هر پیام ساخته می‌شود، در لاگ می‌نشیند، و ارسال نمی‌شود. ثبت‌نام تمام
> می‌شود و **هیچ فروشنده‌ای نمی‌تواند ایمیلش را تأیید کند** — یعنی هیچ‌کس نمی‌تواند وارد شود.
> ضمناً تأخیر ۲۴ ساعته روی تغییر آدرس واریز، که کل کارش خبر دادن است، به یک فایل لاگ خبر می‌دهد.

## گام ۴ — API روی VPS و DNS

### ساخت و اجرا

```bash
useradd --system --home /opt/avex --shell /usr/sbin/nologin avex
git clone <repo> /opt/avex && cd /opt/avex
npm ci --include=dev            # پرچم لازم است: بیلد به tsc نیاز دارد که devDependency است
npm run build --workspace @avex/api
chown -R avex /opt/avex

# فایل تنظیمات فقط برای همین کاربر خوانا باشد: رشتهٔ اتصال دیتابیس و رمز SMTP داخلش است.
install -d -m 750 -o avex -g avex /etc/avex
chown avex /etc/avex/api.env && chmod 600 /etc/avex/api.env
```

### سرویس systemd — API

`/etc/systemd/system/avex-api.service`:

```ini
[Unit]
Description=AVEX Pay API
After=network-online.target

[Service]
Type=simple
WorkingDirectory=/opt/avex/apps/api
EnvironmentFile=/etc/avex/api.env
ExecStart=/usr/bin/node dist/main.js
Restart=always
RestartSec=5
User=avex
# پروسه به هیچ چیزی جز کد خودش و شبکه نیاز ندارد.
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

### سرویس systemd — واچر

`/etc/systemd/system/avex-watcher.service`: همان فایل، با این دو تفاوت:

```ini
Description=AVEX Pay chain watcher
ExecStart=/usr/bin/node dist/watcher.js
```

```bash
systemctl daemon-reload
systemctl enable --now avex-api           # ⚠️ اول این
journalctl -u avex-api -f                 # باید listening بدهد

systemctl enable --now avex-watcher       # بعد این
journalctl -u avex-watcher -f             # باید اسم زنجیره‌هایی که می‌پاید را بگوید
```

> ⚠️ **ترتیب مهم است، یک بار.** کاتالوگ دارایی‌ها (USDT روی ترون و بقیه) وقتی **API** بالا
> می‌آید در دیتابیس نوشته می‌شود. واچر آن را می‌خواند و نمی‌نویسد — پس روی یک دیتابیس تازه،
> واچری که اول اجرا شود چیزی برای گشتن ندارد. برای همین با خطا بالا نمی‌آید و می‌گوید علتش
> چیست. (از این به بعد ترتیب اهمیتی ندارد.)

**واچر روی چه چیزی گارد دارد:** اگر مجموعهٔ زنجیره‌های قابل‌پایش خالی باشد بالا نمی‌آید. یک
واچر که چیزی برای پاییدن ندارد از یک واچر سالم قابل تشخیص نیست، و دیپلوی به این باور ادامه
می‌داد که پرداخت‌ها دیده می‌شوند.

### TLS و DNS

`HOST=127.0.0.1` است، پس API از بیرون دیده نمی‌شود و یک reverse proxy جلویش می‌گذاری. با Caddy
کل فایل تنظیمات این است:

```
api.avexpay.net {
  reverse_proxy 127.0.0.1:3000
}
```

بعد در DNS: یک رکورد **A** برای `api` به IP سرور.

```bash
curl -s https://api.avexpay.net/health     # باید جواب بدهد
```

> **اگر انجام ندهی:** پنل‌ها روی avexpay.net هستند و API‌ای برای صدا زدن ندارند. پلاگین
> ووکامرس هم پیش‌فرضش `https://api.avexpay.net` است، پس هر فروشگاهی خطای اتصال می‌گیرد.

## گام ۵ — preflight: بپرس چه چیزی کار نمی‌کند

```bash
cd /opt/avex
set -a; . /etc/avex/api.env; set +a     # همان تنظیماتی که سرویس می‌بیند
npm run preflight --workspace @avex/api
```

فقط تنظیمات را می‌خواند — نه دیتابیس، نه شبکه، نه کلید — و می‌گوید این دیپلوی **چه کاری
نمی‌تواند بکند**. `BLOCKED` یعنی چیزی که محصول را از کار می‌اندازد؛ `degraded` یعنی انتخابی که
ممکن است عمداً کرده باشی. روی اولی exit 1 می‌دهد، پس یک pipeline می‌تواند رویش گیت بگذارد.

برای یک دیپلوی فقط-TRON خروجی درستش این است:

```
ready     chains.tron
            is watched and needs nothing here: its deposit addresses are the wallets each
            merchant registers, so check the dashboard rather than this list.

verdict: ready
```

**این دستور را بعد از هر تغییر تنظیمات اجرا کن.** ارزانی‌اش نکتهٔ اصلی‌اش است.

## گام ۶ — حساب ادمین (اولین و مهم‌ترین)

پنل ادمین **ثبت‌نام ندارد**. اولین حساب از خط فرمان ساخته می‌شود، و فقط تا وقتی که هیچ حسابی
وجود نداشته باشد:

```bash
cd /opt/avex
set -a; . /etc/avex/api.env; set +a
npm run admin:bootstrap --workspace @avex/api
```

سه چیز می‌پرسد: ایمیل، نام، و رمز (حداقل ۱۴ کاراکتر). **رمز روی صفحه نمایش داده نمی‌شود.**

اگر می‌خواهی از یک password manager بدهی، pipe هم کار می‌کند:

```bash
printf '%s\n%s\n%s\n' 'admin@avexpay.net' 'AVEX Operator' "$PW" \
  | npm run admin:bootstrap --workspace @avex/api
```

رمز هیچ‌وقت آرگومان یا متغیر محیطی نیست: آرگومان در تاریخ شل می‌ماند و تا وقتی دستور اجرا
می‌شود در `ps` برای هر کاربر روی سرور دیدنی است؛ متغیر محیطی در `/proc/<pid>/environ` است.

خروجی یک لینک `otpauth://…` می‌دهد. **همان لحظه** در Authenticator ثبتش کن:

> این راز **یک بار** چاپ می‌شود و هیچ روتی برنمی‌گرداندش. ورود بدون Authenticator کارگر، یک
> چالش ثبت‌نام برمی‌گرداند و **هیچ سشنی** — پس این گام اختیاری نیست. اگر گمش کنی باید ردیف را
> با دست از دیتابیس حذف کنی، چون مسیر bootstrap تا آن موقع بسته شده.

بعد وارد `https://avexpay.net/admin` شو. حساب‌های بعدی از داخل خود پنل ساخته می‌شوند.

> **اگر انجام ندهی:** پنل ادمین وجود دارد و هیچ‌کس هرگز نمی‌تواند واردش شود. هیچ خطایی هم
> نمی‌بینی — فقط ورود کار نمی‌کند.

## گام ۷ — اولین فروشنده

فروشنده‌ها خودشان ثبت‌نام می‌کنند: `https://avexpay.net/dashboard` → ثبت‌نام → تأیید ایمیل.
برای تست، خودت یکی بساز.

بعد داخل داشبورد:

1. **کیف پول واریز TRON** اضافه کن. کلید دست فروشنده می‌ماند؛ ما فقط آدرس را نگه می‌داریم.
   - **اولین** کیف پول هر زنجیره **فوری** فعال می‌شود.
   - کیف پول‌های **بعدی** ۲۴ ساعت صبر می‌کنند و به همهٔ اعضا ایمیل می‌رود. چون یک کیف پول واریز
     همان جایی است که پول می‌نشیند، پس اضافه کردن آدرسِ خودی به pool یک فروشنده یعنی
     **تغییر مسیر درآمد او** — همان تهدید آدرس تسویه، و همان محافظت.
   - سه تا پنج آدرس بده. تطبیق روی TRON بر اساس **مبلغ** است، پس چند کیف پول یعنی چند پرداخت
     همزمان بدون ابهام.
2. یک **API key** بساز.
3. یک **webhook endpoint** ثبت کن.

## گام ۸ — تست سرتاسری روی مبلغ کوچک

این گام را نمی‌شود پرید.

1. فاکتور بساز (از داشبورد یا `POST /v1/organizations/:orgId/checkouts`).
2. با کیف پول واقعی، **همان مبلغ دقیق** را بفرست. مبلغ سنت‌های آخرش عمداً یکتاست.
3. واچر باید در چند ثانیه ببیندش: `journalctl -u avex-watcher -f`
4. وبهوک باید برسد.
5. رسید باید رندر شود.
6. **بعد همین را با گوشی تکرار کن** — QR را با دوربین واقعی اسکن کن. این هرگز انجام نشده.

> **الان می‌توانی روی TRON پول واقعی بگیری.**
>
> یک نکتهٔ تجاری که باید بدانی: روی TRON کمیسیون **روی زنجیره برداشته نمی‌شود** — به حساب
> فروشنده بدهکار می‌شود. پس درآمد به‌صورت مطالبه جمع می‌شود تا زنجیره‌ای که می‌تواند سهم
> بردارد لایو شود؛ آن‌وقت از یک فاکتور EVM بعدی کسر می‌شود، یا با درخواست وصول می‌شود.

# زنجیره‌های EVM — بعد از لایو شدن TRON

سه گام باقی‌مانده فقط برای بایننس/اتریوم/پالیگان لازم است. TRON به هیچ‌کدام نیاز ندارد.

## گام ۱۰ — دیپلوی قراردادها

هر آدرس واریز روی EVM یک **کلون ۸۷ بایتی** است که با CREATE2 ساخته می‌شود. آدرسش یک هش است
روی: کارخانه، آدرس منطق، مقصد، مقصد کمیسیون، و نرخ. یعنی آدرس **به این پارامترها متعهد است** و
هیچ باگی نمی‌تواند بعداً پول را جای دیگری بفرستد.

```bash
# اول بی‌خطر: هزینه را می‌گوید و هیچ چیزی نمی‌فرستد
RPC_URL=https://bsc-dataseed.binance.org node contracts/deploy.mjs --chain bsc --dry-run

# بعد واقعی
DEPLOY_KEY_HEX=0x… RPC_URL=https://… node contracts/deploy.mjs --chain bsc
```

اسکریپت `ForwarderLogic` را دیپلوی می‌کند، بعد `ForwarderFactory` را با آن آدرس، و دو خط تنظیمات
چاپ می‌کند. دو گارد دارد:

- اگر chain id اندپوینت با `--chain` نخواند، **امضا نمی‌کند**.
- از کارخانهٔ دیپلوی‌شده می‌خواهد یک آدرس واریز را پیش‌بینی کند و با آنچه این بیلد استخراج
  می‌کند مقایسه می‌کند. **اختلاف یعنی هر آدرس منتشرشده آدرسی است که کارخانه هرگز نمی‌تواند
  تسویه‌اش کند، و هیچ خطایی هم جایی نیست.** پس در صورت اختلاف تنظیمات را چاپ نمی‌کند.

آن دو خط را در `api.env` بگذار:

```ini
FORWARDER_FACTORIES=bsc=0x…
FORWARDER_IMPLEMENTATIONS=bsc=0x…
FEE_COLLECTORS=bsc=0x…
EVM_RPC_URLS=tron=https://api.trongrid.io/jsonrpc,bsc=https://bsc-dataseed.binance.org,bsc=https://bsc-dataseed1.defibit.io
```

**هر دو خط یا هیچ‌کدام.** کارخانه بدون آدرس منطق، آدرس‌ها را از رشتهٔ خالی استخراج می‌کند:
هگز معتبر، آدرس واقعی، و آدرسی که هیچ‌وقت قابل تسویه نیست. (کد این حالت را تشخیص می‌دهد و آن
زنجیره را کنار می‌گذارد، پس اثرش این است که آن زنجیره بی‌صدا فاکتور صادر نمی‌کند —
`preflight` همین را می‌گوید.)

**چند اندپوینت per chain عمدی است.** پروایدرهای میزبانی‌شده بعضی مناطق را geofence می‌کنند.

> ⚠️ **بعد از لانچ نمی‌شود دوباره دیپلوی کرد.** هر آدرس واریز هشی روی آدرس منطق است، پس
> دیپلوی مجدد یعنی یک مجموعهٔ کاملاً جدید از آدرس‌ها. هر دو آدرس را کنار کامیتی که ساختشان
> ثبت کن.

## گام ۱۱ — کلید تسویه و کیف پول گس

تسویه روی EVM یک تراکنش است که ما امضا می‌کنیم. یعنی یک کلید لازم است.

### این کلید دقیقاً چه کاری می‌تواند بکند

**نمی‌تواند پول هیچ فروشنده‌ای را جایی جز به خودِ آن فروشنده ببرد.** آدرس واریز یک کلون است که
مقصد پرداخت، مقصد کمیسیون و نرخ کمیسیون، **بایت‌های کد خودش** هستند؛ `flush` آن‌ها را با
`EXTCODECOPY` از `address(this)` می‌خواند، هیچ چیزی از فراخوان‌کننده نمی‌گیرد، و عمداً برای همه
قابل صدا زدن است. کارخانه هم نمی‌تواند مسیرش را عوض کند. پس یک کلید دزدیده‌شده به پول هیچ
مشتری‌ای نمی‌رسد، و به آدرس کمیسیون هم نمی‌رسد — آن هم آدرس جداگانه‌ای است که در هر کلون نوشته
شده.

چیزی که **هست**، همان **کیف پول گس** است. دزد می‌تواند موجودی توکن بومی‌اش را خالی کند و
nonce‌ها را اشغال کند تا تسویه‌های خودمان تأیید نشوند، تا وقتی کسی متوجه شود. همین کل ضرر است.

و همین اندازهٔ دفاع درست را مشخص می‌کند: **موجودی را به‌اندازهٔ چند روز گس نگه دار و رویش آلارم
بگذار.** آن‌وقت ریسک یک باک بنزین است، نه درآمد یک فروشنده.

### KMS چیست، و آیا لازمش داری

**KMS** سرویسی است که کلید خصوصی را **خودش نگه می‌دارد و به تو نمی‌دهد**. تو یک هش ۳۲ بایتی
می‌فرستی، امضا را می‌گیری. کلید هیچ‌وقت از آن بیرون نمی‌آید، پس نمی‌شود دزدیدش؛ دسترسی هم
قابل‌لغو و ثبت‌شده است. AWS KMS، Google Cloud KMS و Vault نمونه‌هایش هستند.

**روی هتزنر، لازمش نداری.** دو دلیل:

1. هتزنر KMS مدیریت‌شده ندارد، پس باید از بیرون بگیری — یک حساب جای دیگر و یک وابستگی شبکه
   برای هر تسویه. و یک نکتهٔ فنی که قبل از انتخاب سرویس باید چک شود: اتریوم روی منحنی
   **`secp256k1`** امضا می‌کند، در حالی که پیش‌فرض هر KMS مدیریت‌شده منحنی NIST P-256 است —
   منحنی دیگری است و این امضاها را نمی‌سازد. پشتیبانی از `secp256k1` یک قابلیت جداگانه است که
   همهٔ سرویس‌ها ندارند. AWS KMS دارد (`ECC_SECG_P256K1`)؛ برای بقیه، لیست key spec خودشان را
   بخوان، حدس نزن.
2. مهم‌تر: با توجه به بالا، آن کلید فقط کیف پول گس است. KMS برای محافظت از چیزی است که این کلید
   کنترلش نمی‌کند.

اگر بعداً بخواهی، درزش آماده است: `DerKeyProvider` در `@avex/core` کار سخت را کرده — پارس DER،
نرمال کردن `s` بالا، پیدا کردن recovery id، و اثبات اینکه امضا به همان آدرس recover می‌شود.
فقط صدا زدن API یک سرویس مشخص مانده.

### روی سرور هتزنر، کاری که باید بکنی

کلید در **فایل** می‌رود، نه در متغیر محیطی. `SETTLEMENT_KEY_HEX` در production **رد می‌شود**، و
دلیل رد شدنش «در حافظه بودن» نیست (هر امضاکنندهٔ محلی کلید را در حافظه دارد) بلکه این است که یک
متغیر محیطی تا آخر عمر پروسه در `/proc/<pid>/environ` می‌ماند، در هر core dump می‌آید، و در فایل
یونیت یا `EnvironmentFile` که ست‌اش کرده — و در هر بکاپی از آن فایل.

اول ببین systemd سرورت چند است:

```bash
systemd-analyze --version | head -1
```

**اگر ۲۵۰ یا بالاتر** (اوبونتو ۲۴.۰۴، دبیان ۱۲) — credential رمزشده، بهترین گزینه:

```bash
systemd-creds encrypt --name=settlement-key - /etc/avex/settlement-key.cred
# کلید 0x… را پیست کن و Ctrl-D بزن. متن خام هیچ‌وقت روی دیسک نمی‌نشیند.
```

در فایل یونیت واچر:

```ini
LoadCredentialEncrypted=settlement-key:/etc/avex/settlement-key.cred
Environment=SETTLEMENT_KEY_FILE=%d/settlement-key
```

‏`%d` همان `$CREDENTIALS_DIRECTORY` است: یک tmpfs که فقط داخل namespace همان یونیت مانت
می‌شود، با مود ۰۴۰۰. اگر سرور TPM داشته باشد credential به آن مهر می‌شود؛ اگر نداشته باشد — که
روی Hetzner Cloud ندارد — با یک کلید میزبان که فقط root می‌خواندش رمز می‌شود. باز هم متن خام
روی دیسک، نسخهٔ بکاپ، و تاریخ شل را از میان برمی‌دارد.

**اگر ۲۴۷ تا ۲۴۹** (اوبونتو ۲۲.۰۴ — همان چیزی که هتزنر پیش‌فرض می‌دهد) — `systemd-creds` را
ندارد ولی `LoadCredential` را دارد. همان جداسازی، بدون رمزنگاری روی دیسک:

```ini
LoadCredential=settlement-key:/etc/avex/settlement-key
Environment=SETTLEMENT_KEY_FILE=/run/credentials/avex-watcher.service/settlement-key
```

**قدیمی‌تر، یا هر حالت دیگر** — فقط یک فایل:

```bash
install -m 600 -o avex -g avex /dev/stdin /etc/avex/settlement-key
```

```ini
SETTLEMENT_KEY_FILE=/etc/avex/settlement-key
```

این کفِ کار است و باز هم سمت درست خط قرار دارد: چیزی که اهمیت دارد یک متغیر محیطی خواندنی در
`/proc` است که در هر بکاپ فایل تنظیمات کپی می‌شود، و یک فایل ۰۶۰۰ مالِ کاربر سرویس هیچ‌کدام
نیست.

### دو چیز دیگر

- **`FEE_COLLECTORS` را یک آدرس جدا و سرد بگذار.** کلید تسویه به آن دسترسی ندارد، پس درآمد
  کمیسیون خارج از دسترس این ریسک می‌ماند.
- **آلارم موجودی گس** (گام ۱۲). این تنها دفاعی است که واقعاً به اندازهٔ ریسک است.

> **اگر انجام ندهی:** پرداخت‌ها روی EVM دیده می‌شوند، اعتبار داده می‌شوند، با وبهوک اعلام
> می‌شوند، و **سر جایشان می‌مانند** — جایی که فقط می‌توانند به فروشندهٔ خودشان پرداخت کنند. پس
> پول گم نمی‌شود، ولی گیت‌وی از هر زاویه‌ای سالم به‌نظر می‌رسد جز موجودی فروشنده. واچر در هر
> startup این را با صدای بلند می‌گوید.

## گام ۱۲ — هشدارها و بکاپ

- **`OPERATOR_EMAIL`** را بگذار. هشدارهای بحرانی — کیف پول گسی که در حال ته کشیدن است،
  nonce‌ای که هیچ چیز از آن رد نمی‌شود، تسویه‌ای که revert شده — یک بار در هر ۱۵ دقیقه برای هر
  نوع ایمیل می‌شوند. هشدارهای سبک‌تر در لاگ می‌مانند.
- **موجودی گس در هر پاس تسویه چک می‌شود، فرقی نمی‌کند کاری برای انجام باشد یا نه**، و حدود
  ۱۰ تسویه قبل از ته کشیدن ایمیل می‌زند — یعنی وقتی شارژ کردن هنوز یک تصمیم آرام است. قبلاً
  فقط در برابر همان تراکنشی که می‌خواست بفرستد چک می‌شد؛ یعنی کیف پولی که روی یک زنجیرهٔ خلوت
  ته می‌کشید هیچ‌وقت نگاه نمی‌شد، و آن پیامی که به‌موقع می‌رسید `warning` بود که لاگ می‌شود نه
  ایمیل. تنها ایمیلی که به دستت می‌رسید همان بود که یعنی «تسویه از قبل متوقف شده».
- **کرسری که ۱۰ دقیقه جلو نرفته**، **۵ پایش پشت‌سرهم شکست‌خورده**، یا **فید قیمت معلق شده**
  هم به همان آدرس هشدار می‌دهند. اولی همان خرابی‌ای است که **هیچ‌کس گزارش نمی‌دهد**: انتقال
  مشتری confirm می‌شود، فروشنده چیزی نمی‌بیند، و هر کدام دیگری را متهم می‌کند در حالی که هر
  سیگنال دیگری سالم است.
- **بکاپ دیتابیس با point-in-time recovery.** روی Supabase یک تنظیم است.

## جدول عیب‌یابی: علامت ← علت

| چه می‌بینی | علت واقعی |
|---|---|
| ثبت‌نام تمام می‌شود، ایمیل تأیید نمی‌آید | `SMTP_URL` تنظیم نشده. پیام ساخته و لاگ شده. |
| ایمیل می‌رسد ولی لینکش 404 | `APP_URL` روی آدرس API است، نه صفحات ثابت. |
| پنل ادمین لاگین نمی‌شود | هیچ حساب staff وجود ندارد — گام ۶. |
| پنل‌ها در مرورگر خطای CORS | `DASHBOARD_ORIGINS` تنظیم نشده. |
| «خطای سینتکس» در مایگریشن | از pooler روی ۶۵۴۳ اجرا شده. `DIRECT_DATABASE_URL` روی ۵۴۳۲. |
| `prepared statement "s1" does not exist` | pooler تشخیص داده نشده: `DATABASE_PREPARE=false`. |
| یک زنجیره فاکتور صادر نمی‌کند | `FORWARDER_FACTORIES` یا `FORWARDER_IMPLEMENTATIONS` ندارد. |
| پرداخت رسید، موجودی فروشنده صفر | کلید تسویه نیست — گام ۱۱. |
| وبهوک شکست خورده و هرگز retry نشد | نه `RUN_JOBS_IN_PROCESS` و نه `CRON_SECRET`. |
| فاکتور کوچک رد می‌شود، `amount_below_minimum` | درست است: آن زنجیره گران‌تر از فاکتور تسویه می‌شود. |
| واچر بالا نمی‌آید، «no chain is watchable» | نه `EVM_RPC_URLS` معتبر نه factory. عمدی. |
| واچر بالا نمی‌آید، «no chain has a listed approved asset» | روی دیتابیس تازه قبل از API اجرا شده. یک بار API را بالا بیاور. |

## چه چیزی از سمت من مانده، و چه چیزی از سمت تو

**از سمت من — چیزی نمانده که بتوانم بزنم.** هر گامی که کد بود نوشته و تست شده. سه چیز عمداً
نساخته‌ام:

1. **`KeyProvider` پشت KMS** — یک تصمیم است نه یک متغیر. باید بدانم هاست تو چه چیزی می‌دهد.
2. **صفحات terms و privacy** — اسناد حقوقی دربارهٔ تعهدات یک شرکت واقعی‌اند. تولیدشان کار من
   نیست.
3. **آداپتور Solana** — طراحی شده، پیاده نشده. هیچ چیزی به آن وابسته نیست.

**از سمت تو، به ترتیب:** دیتابیس ← SMTP + DNS ایمیل ← VPS و DNS ← اجرای گام ۶ ← ثبت کیف پول
TRON ← تست با پول واقعی ← اسکن QR با گوشی ← (بعداً) قرارداد، کلید KMS، آلارم موجودی گس.

**آن چیزی که واقعاً نباید از قلم بیفتد:** گام ۶ و آلارم موجودی گس. اولی یعنی پنلی که هیچ‌کس
نمی‌تواند واردش شود؛ دومی یعنی تسویه‌ها بی‌صدا متوقف می‌شوند در حالی که همه‌چیز سالم به‌نظر
می‌رسد.
